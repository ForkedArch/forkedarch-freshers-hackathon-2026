# ForkedArch Freshers Hackathon 2026

## Official Rulebook

> **Organized by ForkedArch**  
> **For:** Batch 2K25  
> **Format:** Fully Online  
> **Total Duration:** 50 Hours

---

# 1. About the Hackathon

ForkedArch Freshers Hackathon 2026 is a beginner-friendly, fully online hackathon designed exclusively for the students of **KUET CSE 2K25 (1-1)**.

The objective is to give participants their first serious experience of:

- Understanding a real-world problem
- Designing a practical solution
- Working collaboratively as a team
- Building a functional software project
- Using modern development tools
- Documenting technical decisions
- Presenting a project professionally
- Working with Git and GitHub
- Using AI-assisted development responsibly

This is not simply a coding contest. Participants are expected to **build, explain, document, and present** a complete solution.

---

# 2. Eligibility

1. Participation is open to **KUET CSE 2K25 — 1-1 students only**.
2. Each participant may belong to **one team only**.
3. Each team must consist of **3/4 members**.
4. Teams must be registered before the registration deadline.
5. Participant information must be accurate and verifiable.
6. Organizers reserve the right to verify participant eligibility.

---

# 3. Team Composition & 5% Mark Boost

Each team must consist of **3/4 students**.

Teams containing **at least one female team member** will receive a **5% boost to their final judging score**.

For example:

> If a team receives 80/100 from the judging criteria, a 5% boost means the adjusted score becomes 84/100.

### Important

- The female member must be an actual registered member of the team.
- A participant cannot be counted as a member of multiple teams.
- The 5% boost is applied to the **final judging score**, not to individual judging categories.
- False representation of team members will result in disqualification.

---

# 4. Hackathon Format

The hackathon will be conducted **entirely online**.

Participants will not be required to gather at a physical venue.

Communication, announcements, submissions, and project evaluation will be conducted through online platforms designated by ForkedArch.

Participants are responsible for having:

- A working computer
- Reliable internet access
- A GitHub account
- Required development tools
- A method of communicating with their teammates

---

# 5. Duration: 50 Hours

The hackathon consists of:

### 48 Hours — Development Period

After receiving their assigned problem statement and challenge information, teams will have **48 consecutive hours** to design and develop their solution.

### Additional 2 Hours — Submission Period

After the 48-hour development period, teams will receive an additional **2 hours exclusively for final project submission and submission verification**.

### Total

**48 hours + 2 hours = 50 hours**

The exact start and end times will be announced by ForkedArch.

---

# 6. Problem Statement

After registration and confirmation, each participating team will receive its assigned:

- Problem statement
- Challenge description
- Relevant requirements
- Expected outcome
- Submission instructions

The problem statement will be delivered through the official communication channel/email designated by ForkedArch.

The development clock begins according to the official time communicated by the organizers.

---

# 7. What Teams Have to Build

Teams must develop a software-based solution addressing the assigned problem.

The solution should demonstrate:

- A clear understanding of the problem
- A logical approach
- Meaningful implementation
- Appropriate use of technology
- A functional or demonstrable prototype
- Clear documentation
- A presentable user experience where applicable

The project does not need to be a massive production-ready application.

A focused, well-executed MVP is preferable to a large project with unfinished or non-functional features.

---

# 8. Technology & Tools

Participants are free to use **any appropriate programming language, framework, library, database, API, development environment, design tool, cloud service, or other software tool**.

There is no mandatory technology stack.

Examples are included below, but are not limited to:

- C / C++
- Python
- Java
- JavaScript / TypeScript
- Go
- Rust
- React
- Next.js
- Node.js
- Express
- Django
- FastAPI
- MongoDB
- PostgreSQL
- Firebase
- Supabase
- Cloud services
- Public APIs
- Open-source libraries

The choice of technology will not automatically determine a team's score.

**Quality, relevance, implementation, reliability, and understanding matter more than the number of technologies used.**

---

# 9. AI Tools Are Allowed

AI-assisted development is **explicitly allowed**.

Participants may use tools such as:

- ChatGPT
- GitHub Copilot
- Claude
- Gemini
- Cursor
- Other AI coding assistants
- AI-based design or development tools

However, AI usage does **not** remove the team's responsibility for the project.

### The core rule is:

> **You may use AI to help build the project, but you must understand and be able to explain what you submit.**

Teams must be able to explain:

- What their project does
- How the system works
- Why they selected their technologies
- How important components work
- How data flows through the application
- How APIs are used
- How the database is structured
- How authentication/authorization works, if applicable
- What AI-generated components were used
- What limitations exist
- What they personally implemented or modified

Judges may ask questions to verify the team's understanding.

---

# 10. AI Usage Transparency

Teams are encouraged to disclose significant AI usage in their `README.md`.

For example:

```text
## AI Usage

AI tools used:
- ChatGPT
- GitHub Copilot

AI was used for:
- Debugging
- Generating initial boilerplate
- Suggesting implementation approaches

Human contribution:
- Architecture
- Feature design
- Integration
- Testing
- Modification and verification
```

This is not intended to punish teams for using AI.

The purpose is to encourage **responsible and transparent AI-assisted development**.

---

# 11. Quality Assurance

Using more tools does not automatically mean a better project.

The judging process will consider the **quality of the final result**.

Teams should test their projects before submission.

At minimum, teams should consider:

- Functional correctness
- Basic error handling
- Input validation
- Stability
- Usability
- Security where relevant
- Responsiveness where relevant
- API reliability
- Database correctness
- Deployment reliability
- Clear documentation

A project with many features but poor reliability may score lower than a smaller project that works exceptionally well.

---

# 12. GitHub Requirement

Every project **must be pushed to GitHub**.

Each team must provide the URL of its project repository during submission.

The repository should contain the project's relevant source code and documentation.

### Recommended repository structure

```text
project-name/
├── README.md
├── src/
├── assets/
├── docs/
├── .gitignore
└── ...
```

The exact structure depends on the technology used.

---

# 13. Git & Commit History

Teams are strongly encouraged to use Git throughout development rather than uploading everything at the very end.

Meaningful commits are recommended.

Examples:

```text
Initial project setup
Implement authentication
Add dashboard
Integrate API
Fix validation issue
Improve responsive layout
Update documentation
```

Teams should avoid intentionally misleading commit histories.

The GitHub repository should represent the team's actual development process as reasonably as possible.

---

# 14. README.md Requirement

A clear and comprehensive `README.md` file is **mandatory**.

The README should allow a technically competent reader to understand the project without requiring the team to verbally explain every basic detail.

At minimum, the README should include:

### 14.1 Project Name

The name of the project.

### 14.2 Project Overview

A concise explanation of what the project does.

### 14.3 Problem Statement

Explain the problem your team was assigned and the problem you are solving.

### 14.4 Proposed Solution

Explain how your project addresses the problem.

### 14.5 Features

List and explain the major features.

### 14.6 Technology Stack

Clearly identify the technologies used.

Example:

```text
Frontend: React
Backend: Node.js + Express
Database: MongoDB
Authentication: JWT
Deployment: Vercel + Render
```

### 14.7 System Workflow

Explain the complete workflow of the application.

For example:

```text
User
  ↓
Frontend
  ↓
API
  ↓
Authentication
  ↓
Backend Logic
  ↓
Database
  ↓
Response
  ↓
Frontend
```

A diagram may be included where useful.

### 14.8 Architecture

Explain the major components of the system and how they interact.

### 14.9 Setup Instructions

Explain exactly how another developer can run the project locally.

### 14.10 Environment Variables

Document required environment variables without exposing secret values.

Example:

```text
DATABASE_URL=
API_KEY=
JWT_SECRET=
```

Never commit real secrets.

### 14.11 API Documentation

If your project uses an API, explain the important endpoints and their purpose.

### 14.12 Database Structure

Explain important collections/tables/models where applicable.

### 14.13 AI Usage

Mention AI tools used and what they were used for.

### 14.14 Testing / Quality Assurance

Explain how the project was tested.

### 14.15 Limitations

Clearly mention known limitations.

### 14.16 Future Improvements

Mention realistic features or improvements that could be implemented later.

---

# 15. Explain Every Major Component

The README must not simply say:

> "Built using React, Node.js, MongoDB and AI."

That is not sufficient.

Teams should explain **how those technologies were used in their particular project**.

For example:

Instead of:

```text
Backend: Node.js
```

Prefer:

```text
Backend: Node.js + Express

The Express server receives requests from the React
frontend, validates incoming data, performs the required
business logic, communicates with MongoDB, and returns
JSON responses to the client.
```

The quality of technical explanation will be considered during evaluation.

**3:00 minutes**

1. The problem
2. The proposed solution
3. The project
4. Important features
5. How it works
6. The technology used
7. A short demonstration

The video should prioritize clarity over visual effects.

# 20. Late Submission

Late submissions are generally not accepted.

If a team encounters a genuine technical problem immediately before the deadline, they should contact the organizers **before the deadline whenever possible**.

The organizers may, at their discretion, determine whether an exceptional submission can be considered.

Technical difficulties such as:

- Slow internet
- Computer problems
- GitHub issues
- Deployment failure

are the team's responsibility to manage as far as reasonably possible.

Teams are strongly advised to submit early.

# 21. Judging Criteria

Projects will be evaluated using the following criteria:

| Criterion                        |   Weight |
| -------------------------------- | -------: |
| Problem Understanding & Impact   |      20% |
| Innovation & Creativity          |      20% |
| Technical Implementation         |      25% |
| UI/UX & Usability                |      15% |
| Completeness & Quality Assurance |      10% |
| Presentation & Communication     |      10% |
| **Total**                        | **100%** |

---

# 22. Problem Understanding & Impact — 20%

Judges may consider:

- How clearly the team understands the problem
- Whether the proposed solution addresses the actual problem
- Practical usefulness
- Potential impact
- Relevance of the solution

---

# 23. Innovation & Creativity — 20%

Judges may consider:

- Originality
- Creativity
- Novel approach
- Unique features
- Effective use of technology

Innovation does not necessarily mean inventing something completely new.

A creative improvement to an existing concept can also score highly.

---

# 24. Technical Implementation — 25%

Judges may consider:

- Code quality
- Architecture
- Technical decisions
- Correctness
- Appropriate technology selection
- API/database implementation
- Integration
- Scalability considerations where relevant
- Technical understanding

Teams may be questioned about their implementation.

---

# 25. UI/UX & Usability — 15%

For projects with a user interface, judges may consider:

- Ease of use
- Visual clarity
- Navigation
- Responsiveness
- Accessibility where applicable
- Consistency
- Overall user experience

Projects that do not require a traditional graphical interface will be evaluated according to their relevant interaction design.

---

# 26. Completeness & Quality Assurance — 10%

Judges may consider:

- Whether the core features work
- Stability
- Error handling
- Testing
- Validation
- Documentation
- Overall polish

A smaller project that works reliably can score better than an ambitious but incomplete project.

---

# 27. Presentation & Communication — 10%

Judges may consider:

- Clarity of the presentation
- Quality of the demonstration
- Ability to explain the solution
- Quality of the presentation video
- Ability to answer technical questions

---

# 28. 5% Female Team Member Boost

After the judging score is calculated out of 100, teams satisfying the female-member requirement will receive a **5% score boost**.

Example:

```text
Original score: 82/100

5% boost:
82 × 1.05 = 86.1

Final adjusted score: 86.1/100
```

The adjusted score will be used for ranking, subject to the organizers' final verification.

# 30. Academic & Technical Integrity

Participants must submit work created by their registered team during the hackathon period, subject to the allowed tools and resources described in this rulebook.

The following are prohibited:

- Submitting another team's project
- Copying another participant's complete project
- Purchasing or obtaining a pre-built solution and presenting it as original work
- Submitting a project created before the hackathon as the primary solution
- Falsifying project information
- Falsifying team membership
- Deliberately misleading judges about authorship or implementation

# 45. Recommended Team Workflow

Teams are encouraged to follow a structured workflow.

### Step 1 — Understand

Read the problem carefully.

Identify:

- Users
- Problem
- Constraints
- Expected outcome

### Step 2 — Plan

Define the MVP.

Decide:

- Core features
- Technology stack
- Team responsibilities
- Timeline

### Step 3 — Design

Create:

- User flow
- UI sketches
- Architecture
- Database design where applicable

### Step 4 — Build

Implement the core functionality first.

### Step 5 — Integrate

Connect:

- Frontend
- Backend
- Database
- APIs
- External services

### Step 6 — Test

Test the important workflows.

### Step 7 — Document

Write the README while the project is being developed.

### Step 8 — Present

Record the presentation video.

### Step 9 — Submit

Push the final version to GitHub and complete the submission form.
